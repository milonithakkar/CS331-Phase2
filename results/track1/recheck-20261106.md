# Re-check of Track 1 numbers (6 Nov 2026)

Some Track 1 numbers were marked "needs rerun" because the raw JSON did not keep those fields.
We re-ran the tools directly on the committed pcaps. Every command below can be run again.

- Mac: TShark 4.6.8 (Homebrew).
- Lab: `cn-lab` image from `code/Dockerfile` (TShark 4.4.19, FoxIO tag v0.18.6 as `ja4`, FoxIO main c6469a7 as `ja4-main`).
- Extra: FoxIO tag v1.0.1 (31 Aug 2026), built with
  `cargo install --locked --git https://github.com/FoxIO-LLC/ja4 --tag v1.0.1 ja4`
  (its binary reports `ja4 0.18.6`).

## L3: offload and the SYN-ACK values (`tls_offload_on.pcap`, `tls_offload_off.pcap`)
```sh
tshark -r captures/pcaps/tls_offload_on.pcap  -Y "tcp.dstport==443 && tcp.len>1000" -T fields -e frame.len -e tcp.len
tshark -r captures/pcaps/tls_offload_off.pcap -Y "tls.handshake.type==1" -T fields -e frame.len -e tcp.segment.count
tshark -r captures/pcaps/tls_offload_on.pcap  -Y "tcp.flags.syn==1" -T fields -e tcp.flags.ack -e tcp.options.mss_val -e ip.ttl -e tcp.options.wscale.shift -e tcp.window_size_value
```
| | result |
|---|---|
| offload on | ClientHello in 1 frame of 1586 bytes (TCP payload 1520), 3 of 3 connections |
| offload off | ClientHello in 2 frames: 1514 + 138 bytes, 3 of 3 connections |
| client SYN | MSS 1460, TTL 64, wscale 10, window 64240 |
| SYN-ACK seen in the container | MSS 65495, TTL 63, wscale 7, window 65408 |

`summary.md` column `biggest_frame` is the biggest frame in the whole pcap (any direction), not the ClientHello frame.
That is why it shows 4913 / 2962 and not 1586.

## L5: one Chromium, how many JA4s (`tls_chromium_repeat.pcap`, 50 ClientHellos)
```sh
tshark -r captures/pcaps/tls_chromium_repeat.pcap -Y "tls.handshake.type==1" -T fields -e tls.handshake.ja4 | sort -u | wc -l
tshark -r captures/pcaps/tls_chromium_repeat.pcap -Y "tls.handshake.type==1" -T fields -e tls.handshake.ja4_r | cut -d_ -f4 | cut -d, -f1 | sort -u
ja4 --json captures/pcaps/tls_chromium_repeat.pcap | grep -o '"ja4":"[^"]*"' | sort -u | wc -l
```
| tool | distinct JA4 in 50 hellos |
|---|---|
| TShark 4.4.19 (lab) | 15 |
| TShark 4.6.8 (Mac) | 15 |
| FoxIO tag v0.18.6 (`ja4` in the lab) | 15 |
| FoxIO tag v1.0.1 | 1 |
| FoxIO main c6469a7 (`ja4-main`) | 1 |

The first signature algorithm of the 50 hellos takes 15 values, all GREASE:
`0a0a 1a1a 2a2a 3a3a 4a4a 5a5a 6a6a 7a7a 8a8a 9a9a baba caca dada eaea fafa`.
FoxIO's fix is commit d66336e "fix(rust): ignore grease in sigalgs", first released in tag v1.0.1.
JA3: 50 distinct values in the same 50 hellos.

## L7: DNS and the DoH run
```sh
tshark -r captures/pcaps/tls_ech_on.pcap  -Y "tls.handshake.type==1" -T fields -e tls.handshake.extensions_server_name | sort | uniq -c
tshark -r captures/pcaps/tls_ech_on.pcap  -Y "dns.flags.response==0" -T fields -e dns.qry.name | sort | uniq -c
tshark -r captures/pcaps/tls_ech_doh.pcap -Y "dns.flags.response==0" -T fields -e dns.qry.name | sort | uniq -c
```
- ECH on: SNI `cloudflare-ech.com` (2 hellos), but plain DNS asks for `crypto.cloudflare.com` (2 queries).
- DoH run: all 12 ClientHellos go to `cloudflare-dns.com`, and that name itself is looked up over plain DNS.
  The target page output is empty, so the DoH run did not load the page. It is not a result.

## QUIC: what is inside the client packets sent after the connection ID switch
```sh
tshark -r captures/pcaps/quic_curl.pcap -Y "quic.long.packet_type==0 && udp.dstport==443" -T fields -e udp.srcport -e quic.dcid -e quic.frame_type
```
- TShark 4.6.8 decrypts every client Initial, also the ones sent with the server's connection ID.
- Those later packets carry only ACK (0x02) and PADDING (0x00) frames, no CRYPTO frames.
  So in these captures the ClientHello (and JA4) is complete before the switch.
